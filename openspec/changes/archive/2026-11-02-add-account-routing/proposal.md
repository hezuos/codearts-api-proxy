# Proposal

## Why

上游按华为账号限制 3 个并发会话，且该配额是**账号级共享**的：官方 IDE、其他客户端会同时占用，代理看不到外部在途数。当前一个 API Key 只能绑定一个账号，撞限时除了排队没有任何回旋余地。

同时，对话标识目前由"系统提示词 + 首条用户消息 + 账号"哈希得到。系统提示词会随会话推进而变化（实测 27002 → 28063 字符），导致同一对话的标识不断翻新、链状态反复冷启动；账号一旦切换，标识必然改变。

用户侧的实际诉求是把多个华为账号的容量当作**一个池**来用：希望在 **Users 级别**也能生成 API Key，由代理在该用户所属账号之间自动分配请求，把账号级并发配额叠加起来。

## What Changes

- 一个 API Key SHALL 能绑定多个 ProviderAccount，请求按策略选择账号。
- **新增用户级（User scope）API Key**：不绑定单一账号，候选集为该用户全部可用账号，按分配策略在账号间调度。
- 分配粒度 SHALL 由用户在创建时显式选择，必选且**预选"对话连续"**，可改选"按请求"；选择"按请求"时界面 SHALL 说明其会牺牲上游缓存局部性。
  - `conversation`（对话连续）：新对话按轮询游标分配账号，同一对话后续轮次粘住该账号。
  - `request`（按请求轮询）：每个请求推进轮询游标重新选账号，不保持对话绑定。
- 对话标识 SHALL 与账号解耦，并在系统提示词漂移时保持稳定；来源优先级为 `codearts.chat_id` → `X-Conversation-Id` 请求头 → 首条用户消息指纹。
- 账号选择采用"按对话粘性 + 仅在撞限/凭证失效/模型不可用时迁移"（账号级 Key），用户级 Key 在此之上叠加轮询分配。
- 撞限或凭证失效的账号进入冷却窗口；全部账号不可用时排队等待，超出等待上限返回 429。
- 会话与链状态改按 (Key, Account) 复合键存储，避免跨账号串用上游消息标识。
- 凭据刷新、模型列表、管理界面按账号维度展示与操作；用户级 Key 的创建、列表、删除与粒度切换在管理界面单独分区提供。

## Capabilities

### New Capabilities

- `user-api-key`: 用户级 API Key 的作用域与生命周期、两种分配粒度策略、轮询游标、对话绑定表与失败迁移行为。

### Modified Capabilities

- `account-binding`: 新增"单 Key 多账号池"、"按对话粘性路由"与"故障迁移/冷却"要求；新增用户级 Key 与账号解绑的关系（解绑账号不影响用户级 Key，用户级 Key 的候选集相应缩小）；修正"会话只属于 Key"的要求为按 (Key, Account) 归属。
- `hierarchical-store`: 将"Key-Session 严格 1:1"修正为"每个 (Key, Account) 组合各持有一个会话"；新增用户级 Key 的存储路径、启动加载与级联删除要求。
- `chain-divergence-detection`: 新增"对话标识稳定且与账号无关"的要求，明确标识来源优先级与"无可用来源时不做随机伪装"。
- `codearts-request-forwarding`: 新增"按健康度选择账号"与"配额/凭证/模型不可用时迁移到下一个账号"的要求；新增用户级 Key 下两种分配粒度的路由行为。

## Impact

- 代码（鉴权上下文，受影响面窄）：`api-key-store.ts` 定义 `AuthContext` 判别联合；`authenticate-api-key.ts` 装配；`request-context.ts` 挂载类型；`routes/openai.ts` 消费 `auth.session` / `auth.providerAccountId`，需按作用域分支解析账号与会话。`routes/provider-accounts.ts`、`routes/huawei-auth.ts`、`routes/web-ui.ts`、`routes/admin.ts` 与限流器 keyGenerator 只读取 `userId` / `apiKeyId`，**不受影响**。
- 代码（存储）：内存会话索引由单值改为 (Key, Account) 复合键；位置索引显式携带作用域；新增用户级 Key 目录与其写入、加载、级联删除分支；写盘、删除与吊销按作用域分支，避免"无账号"被当作"不落盘"，也避免删除时磁盘文件残留导致重启后复活。
- 代码（路由）：请求入口增加账号选择、轮询游标与失败迁移；`routes/openai.ts` 的聊天处理需在选择账号后再取会话。
- 代码（认证分流）：`authenticate-ui.ts` 的 Web UI Cookie 认证与 API Key 认证共用密钥校验入口，SHALL 按作用域分流——Cookie 只接受账号级 Key，否则"重新生成密钥"会签发出没有会话的新 Key。
- 代码（密钥生命周期）：`routes/web-ui.ts` 的"重新生成账号密钥"当前会吊销该用户全部活跃密钥，SHALL 收窄为只作用于账号级 Key；`routes/admin.ts` 的密钥列表需增加用户级 Key 分区，其删除端点需按作用域拼路径，其刷新端点需对无自有凭据的用户级 Key 返回明确 4xx 而非 500。
- 代码（并发）：闸门复用现有的按账号计数，选择器复用其既有只读统计接口 `getUpstreamGateStats` 判定空槽，不新增重复接口；上游层既有的同账号重试策略不变，跨账号迁移发生在其耗尽之后。
- 代码（错误分类，行为变更）：闸门排队超时当前抛普通 Error、经错误映射落到 502，SHALL 改为抛 `UpstreamConcurrencyError`，使排队超时与上游撞限统一为 HTTP 429 + `Retry-After`。该变更同时作用于账号级 Key 的既有响应码。
- 刷新：调度按 (Key, Account) 遍历；用户级 Key 无自有会话，天然不进入调度。
- 兼容性：已有单账号 Key 行为不变；`providerAccountId` 保留为首选账号以兼容旧数据；旧 Key 缺省视为账号级，缺省分配粒度视为"对话连续"。
- 内部顺序：对话标识稳定化是本 change 的前置子任务，需先完成再做粘性路由与轮询分配。
- 部署边界：轮询游标与对话绑定表为进程内状态，对话粘性保证以单个代理实例为边界；多实例部署下各实例独立分配，且每实例各自按 3 槽/账号放行，会放大单账号的实际上游并发占用。
