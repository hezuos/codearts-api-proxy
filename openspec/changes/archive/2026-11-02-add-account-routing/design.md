# Design

## Context

参见 proposal.md。当前实现的三处单值假设决定了改造面：Key 只记录一个账号；内存会话索引以 Key 为主键；对话标识把账号与系统提示词一起哈希。并发闸门已经按账号计数，这是可以复用的正确抽象。

第二个约束来自 v2 通道的实测结论：上游请求体不含 `chat_id` / `parent_message_id`，对话完全由客户端回传的 `messages` 承载，上游无服务端会话状态。因此跨账号切换**不会丢失对话内容**——代价落在代理侧的链状态与缓存估算精度，而不是上游的上下文正确性。这一点是用户级 Key 能做请求级轮询的前提。

第三个约束是磁盘布局：Key 当前嵌在账号目录下（`users/{userId}/accounts/{accountId}/keys/{keyId}/`），且 `session.json` 与 Key 同级。用户级 Key 天然不属于任何单一账号，需要一个新的目录层级。

第四个约束来自并发闸门的调用位置：取槽发生在上游层**内部**（`chat.ts` 与 `chat-stream.ts` 中按 `session.providerAccountId` 调用 `acquireUpstreamSlot`），而取槽是**异步**的。闸门的排队超时默认为 120 秒，且上游层已内置同账号重试（默认 2 次、1.5 秒起指数退避）。因此"选择器挑一个账号"与"真正拿到并发槽位"之间存在一段无法用取槽接口本身观测的窗口——这是本设计必须显式处理的部分。

第五个约束是多实例部署：刷新任务已通过 `IS_MASTER_NODE` 支持主从分工，项目文档也记录了"多进程部署时各实例状态独立"。本设计的轮询游标与对话绑定表均为进程内状态，因此在多实例部署下粘性保证只在单实例内成立；并发闸门同样是进程内的，每个实例各自按 3 槽/账号放行，多实例会放大单个账号的实际上游并发占用。

第六个约束是错误分类：闸门排队超时目前抛出普通 `Error`，经错误映射落到 502；而 429 + `Retry-After` 目前只属于上游 TM.00001041 重试耗尽时抛出的 `UpstreamConcurrencyError`。两条路径语义相同（都是并发受限），本设计将它们统一。

## Goals / Non-Goals

**Goals:**

- 同一 Key 内可在多账号间选择，且选择结果可预测、可观测。
- 对话身份跨账号、跨系统提示词变化保持稳定。
- 单账号 Key 的行为与升级前完全一致。
- 用户级 Key 能把多个账号的容量当作一个池使用，分配粒度由用户显式选择。

**Non-Goals:**

- 不做跨 Key 或跨用户的账号共享。
- 不做按模型/按请求类型的精细化路由（如"某模型只走某账号"）。
- 不持久化粘性映射、轮询游标与冷却状态（进程重启后重新分配）。
- 不做账号内 Key 之间的轮询：容量按账号计，凭证只从该账号的可用 Key 中取其一。
- 不引入服务端的模型权限目录；账号间模型可见性差异靠失败迁移兜底。
- 不重构上游层的同账号重试策略；只定义它与跨账号迁移的先后顺序。
- 不做跨实例的粘性、游标或冷却状态共享（需要外部协调组件，超出本 change 范围）。

## Decisions

**1. 数据模型用"首选账号 + 账号列表"扩展，而非新建账号池实体**

保留 `providerAccountId` 作为首选，新增账号列表字段。旧数据无需迁移，回滚后仍可用；新建池实体会牵动管理界面、Key 创建流程与存储布局，收益不抵成本。

用户级 Key 复用同一模型：`providerAccountId` 留空、账号列表为空表示"候选集 = 该用户全部可用账号"，另用 `scope` 字段区分二者。旧数据缺 `scope` 时按账号级解释，缺分配粒度时按"对话连续"解释。

现有的 `getUserApiKey(userId)` 返回该用户第一个未吊销 Key 的 `keyHash`（迁移后是 SHA-256 哈希而非原始密钥），且当前无调用点。加入用户级 Key 后它可能返回用户级 Key 的哈希，语义将漂移——该函数 SHALL 被删除，或改为只返回账号级 Key。

**2. 会话按 (Key, Account) 复合寻址，磁盘布局不变**

磁盘路径本来就同时包含账号与 Key，天然支持同一 Key 在多个账号下各有一份会话；只需把内存索引从单值改为嵌套映射，并按组合遍历刷新任务。

**3. 对话标识按来源链解析，任一来源都不含账号与系统提示词**

对话标识必须同时满足：同一对话跨轮稳定、跨账号不变、不含系统提示词。实测 opencode 客户端**不发送** `codearts.chat_id` 扩展字段，因此不能只依赖该字段，否则该来源永远不成立。

来源优先级：请求体 `codearts.chat_id` → `X-Conversation-Id` 请求头 → 首条用户消息内容指纹。三者都不可得时（消息中无 user 角色）**不绑定对话**，按请求粒度处理。

兜底指纹依赖"客户端每轮回传完整历史"这一 v2 通道前提；因为指纹只取首条用户消息，系统提示词漂移不再影响它。备选的服务端会话注册表（前缀匹配 + TTL）留作后续增强。

**4. 账号级 Key 采用粘性优先、容量次之，不主动轮询**

对于绑定具体账号列表的 Key，选择顺序为：同对话上次使用的账号 → 其余健康且有容量的账号。主动轮询会让同一对话在账号间来回跳，既打断上游缓存也增加迁移次数。粘性映射仅存内存，带空闲超时与容量上限。

用户级 Key 的轮询分配是另一种策略变体，见决策 7–10；两者的冷却、迁移与取槽共用同一机制。

**5. 冷却状态放在选择器内，不进闸门；槽位可用性复用闸门既有的只读统计接口**

闸门负责"能不能发"，选择器负责"往哪发"。撞限冷却沿用闸门的恢复窗口（约 60 秒）；凭证失效冷却更长（约 5 分钟），避免反复撞同一个坏账号。闸门已有的按账号自适应降级继续保留，两者互补。

取槽是异步的且发生在上游层内部，选择器无法通过取槽接口本身判断某账号此刻是否有空槽——若直接选中一个已饱和的账号，请求会在闸门里排队至多 120 秒（`UPSTREAM_QUEUE_WAIT_TIMEOUT_MS`），而不是迁移到其他账号，负载均衡将形同虚设。闸门已导出同步只读统计 `getUpstreamGateStats(accountId)`（返回 `active` / `queued` / `limit`），选择器 SHALL 复用它并派生"是否有空槽"（`active < limit && queued === 0`），SHALL NOT 新增重复的闸门接口。

两套机制的分工必须分清：闸门的自适应降级在撞限后把该账号的有效上限降一档（最低 1），影响的是"该账号还能并发几个"；选择器的冷却把该账号整个移出候选集，影响的是"该账号还参与不参与分配"。只做前者，选择器仍可能选中一个只剩 1 槽的账号；两者叠加才构成完整的熔断。

**6. 迁移发生在一个请求内，且每个账号最多一次；跨账号迁移发生在同账号重试耗尽之后；两条并发受限路径统一为 429**

上游层已内置同账号重试（撞限后按 `UPSTREAM_CONCURRENCY_RETRY_MAX` 指数退避重试，默认 2 次、1.5 秒起）。本设计**不改**这层重试，而是在其耗尽抛出 `UpstreamConcurrencyError` 之后，由选择器执行跨账号迁移。因此一次撞限到换账号的实际时延包含同账号重试的退避时间，这是已知代价。

跨账号迁移时 SHALL 释放该账号已获取的并发槽位、标记冷却、换下一个候选账号重新走完整取槽流程。候选总数受账号数约束，天然避免循环。全部失败时只向客户端返回一个终态错误。

闸门排队超时（`UPSTREAM_QUEUE_WAIT_TIMEOUT_MS`）目前抛出的是普通 `Error`，经错误映射落到 502，与上游撞限路径的 429 + `Retry-After` 不一致。两条路径语义相同，SHALL 统一：闸门排队超时 SHALL 抛出 `UpstreamConcurrencyError`，使客户端只需处理一种并发错误码。该改动同时作用于账号级 Key 的既有响应码，属于有意的行为变更。

**7. 用户级 Key 是选择器的策略变体，不另建调度器**

用户级 Key 与账号级 Key 共用一个选择器，差异只有两点：候选集来源（动态全量 vs 显式绑定列表）与分配策略（轮询 vs 粘性优先）。若实现两套调度，冷却、迁移、闸门取槽都要写两遍，且两套语义会随时间漂移。

**8. 分配粒度是 Key 级字段，创建时必选，预选"对话连续"**

`balancingPolicy: "conversation" | "request"`。字段必填，管理界面以二选一控件呈现并预选"对话连续"，用户可改选"按请求"。

预选"对话连续"的理由：请求级会牺牲上游缓存局部性，而其收益（更充分利用单账号 3 槽）对多数场景边际；对话连续在多账号场景下同样能把并发会话摊开，且无副作用。允许显式改选以覆盖批量/CI 短请求等确实需要极限摊薄的场景。

**9. 轮询游标按用户级 Key 存内存，两种粒度共用一个游标**

游标是单调递增的整数，对候选集取模得到目标账号。对话连续策略在**新对话首次分配**时推进游标；按请求策略在**每个请求**时推进游标。游标随进程重启归零——重启后重新分配不影响正确性。

游标 SHALL 带有界：每个用户级 Key 的游标只服务一个 Key，不按账号数增长。

**10. 对话绑定表按 (用户级 Key, 对话标识) 寻址，与候选集下标解耦**

绑定表存 `Map<keyId, Map<conversationId, accountId>>`，带空闲超时与容量上限。存 accountId 而非候选集下标：账号增删只改变候选集，不影响既有绑定——账号被解绑后，其上的绑定在下一轮请求时因账号不可用而自然失效并重新分配。

绑定表与游标均为进程内状态，重启后清空；这 SHALL 被记录在可观测日志中（本次选择依据为"无绑定"而非"绑定命中"），以免把重启误读为策略异常。

**11. 鉴权上下文改为判别联合**

`AuthContext` 从单值结构改为 `{ kind: "account" } | { kind: "aggregate" }` 两种形态：账号级 Key 携带单一账号与会话，用户级 Key 携带分配策略而**不携带会话**，由请求入口经选择器解析出具体账号、Key 与会话。

实际受影响的代码面很窄：只有 `api-key-store.ts`（定义）、`authenticate-api-key.ts`（装配）、`request-context.ts`（类型挂载）与 `routes/openai.ts`（消费 `auth.session` / `auth.providerAccountId`）。`routes/provider-accounts.ts`、`routes/huawei-auth.ts`、`routes/web-ui.ts`、`routes/admin.ts` 与限流器的 keyGenerator 都只读取 `userId` / `apiKeyId`，判别联合下无需分支。

**12. 用户级 Key 的存储路径独立于账号目录；作用域在位置索引中显式表达**

`data/users/{userId}/keys/{keyId}/key.json`。用户级 Key 没有自有会话，因此目录内只有 `key.json`。解绑账号不删除用户级 Key（它聚合剩余账号）；删除用户则级联删除用户级 Key 目录。

内存位置索引 `keyLocation` SHALL 增加显式的 `scope` 字段，SHALL NOT 继续用空字符串兼作作用域标记——现有的 `writeApiKey`、`setSession` 与 `deleteKey` 都以 `loc.accountId` 的真值判断分支，继续复用空字符串会让"无账号"与"作用域未知"两种状态无法区分。用户级 Key 的写入 SHALL 走独立的用户级路径分支，SHALL NOT 因 `accountId` 为空而跳过落盘；吊销状态同样必须落盘。

删除 SHALL 同时作用于磁盘文件与内存索引：现有的 `deleteKey` 按 `accountId` 拼路径，用户级 Key 的 `accountId` 为空会拼出不存在的路径，导致内存索引被清而磁盘文件残留，重启后 Key 复活。

删除用户时 SHALL **显式**把用户级 Key 从内存索引（`apiKeys` / `apiKeysByHash` / `keyLocation`）中移除。仅靠删除用户目录不足以做到这一点——目录删除不会触及内存索引，残留的用户级 Key 将继续通过认证。

**13. 候选集以"可用账号"为准，判定口径三条件合取**

用户级 Key 的候选集 SHALL 为该用户满足以下全部条件的账号：账号状态为 `active`；存在未吊销的账号级 Key；该账号级 Key 持有可用的会话凭证。任一条件不满足的账号 SHALL 退出候选集，但其数据 SHALL 保留（等待凭证刷新或账号状态恢复后重新进入）。候选集 SHALL 在每次请求时重新求值，以反映账号解绑与吊销的即时影响。

**14. 管理界面落点：Admin 面板新增用户级 Key 分区**

用户侧页面（`public/index.html`）是登录页、`public/success.html` 是一次性密钥展示页，二者都不是密钥管理界面；唯一的密钥管理界面是 Admin 面板，且当前密钥**嵌套在账号之下**。用户级 Key 不属于任何账号，因此在 Admin 面板新增**按用户维度**的"用户级 Key"分区，与账号下的密钥列表并列展示，并显式标注作用域与分配粒度。

用户级 Key 只能由 Admin 创建：华为账号登录流程（`huawei-auth.ts` 三处签发点）每处都绑定具体账号，天然只产出账号级 Key，SHALL NOT 改动登录流程。

原始密钥 SHALL 在创建接口的响应中一次性返回给操作者，后续列表接口只暴露哈希。交付交互沿用 `success-key-once` 能力的告警横幅、确认与遮罩流程；SHALL NOT 依赖 `/api/ui/login-result`（该端点返回的是 Cookie 中的密钥，且忽略请求的 `keyId` 参数），SHALL NOT 声称服务端只允许展示一次——既有能力的"一次性"是客户端遮罩语义，新标签页仍可再次显示。

**15. UI Cookie 认证只接受账号级 Key**

Web UI 的 Cookie 认证与 API Key 认证共用密钥校验入口。用户级 Key SHALL NOT 能作为 UI Cookie 使用：UI 的"重新生成密钥""刷新账号令牌"等操作需要单一账号的身份与该账号的会话，而用户级 Key 既不绑定账号也不持有会话。把它放进 Cookie 路径会让"重新生成密钥"签发出一个没有会话、因而永远无法通过校验的新密钥，使操作者被立即踢出。

## Risks / Trade-offs

- **迁移导致同一对话跨账号，上游缓存断裂** → 只迁移不轮询；迁移仅在撞限、凭证失效或模型不可用时发生。
- **多实例部署下，对话粘性只在单实例内成立** → 粘性保证以单代理实例为边界在 spec 中明示；多实例需要外部协调组件，超出本 change 范围。
- **多实例部署下闸门会放大单账号并发占用** → 每个实例各自按 3 槽/账号放行，实例数即倍数；撞限由上游层的自适应降级与失败迁移兜底，但多实例部署时仍应下调 `UPSTREAM_MAX_CONCURRENCY`。
- **闸门排队超时改为 429 会改变账号级 Key 的既有响应码**（502 → 429） → 有意的行为变更：两条并发受限路径语义相同，统一后客户端只需处理一种错误码。
- **内存粘性、轮询游标与冷却状态重启丢失** → 重启后按容量重新选择，可接受；日志会记录本次选择依据（"无绑定"而非"绑定命中"）。
- **选中饱和账号后会在闸门排队至多 120 秒** → 选择器复用闸门既有的只读统计按空槽优先排序候选；探针与取槽之间的竞态窗口由失败迁移兜底。
- **撞限到换账号的时延被同账号重试放大**（默认 2 次、1.5 秒起指数退避）→ 已确认接受该代价，不改上游层重试策略；可在配置层下调 `UPSTREAM_CONCURRENCY_RETRY_MAX` 缓解。
- **多账号下会话文件成倍增长** → 每条会话本就随账号存在，磁盘开销可接受，且便于独立刷新。
- **选择器与闸门之间的竞争** → 统计只用于排序，取槽仍由闸门串行化；探针失准只会导致一次排队，不会导致超发。
- **凭证失效冷却期过长会浪费容量** → 冷却期内仍保留该账号，到期自动恢复；管理员可通过界面查看状态。
- **按请求轮询丢失上游缓存局部性** → 已确认接受；对话连续策略作为默认预选，把该代价限定在用户显式选择的场景。上游是否真有按租户的前缀缓存尚无证据，幅度未知。
- **请求级轮询使同一对话的各轮散落到不同账号** → v2 上游无服务端会话状态，对话内容由客户端回传承载，不影响正确性；仅代理侧链状态与缓存估算精度下降。
- **账号间模型权限不一致导致间歇性失败** → 把"模型不可用"纳入可迁移错误，配合失败迁移换账号。
- **用户级 Key 与账号级 Key 语义并存增加界面复杂度** → Admin 面板内独立分区展示，明确标注作用域与分配粒度。
- **首条消息指纹兜底可能让两个同首句的对话共享绑定** → 仅影响分配均匀度，不影响正确性（v2 无状态）。
- **"重新生成账号密钥"误伤用户级 Key** → 该操作 SHALL 只作用于账号级 Key，spec 已显式约束。
- **Admin 删除账号缺少"最后一个账号"守卫，与 Web UI 不一致** → Web UI 的解绑接口有该守卫（至少保留一个账号），Admin 的删除接口没有，项目约定同样要求至少保留一个账号。本 change 对空候选池做防御性处理，但守卫补齐建议单开 issue。

## Migration Plan

1. 先做对话标识稳定化（本 change 的前置子任务），确保迁移不改变对话身份。
2. 扩展数据模型为可选字段，旧 Key 按首选账号处理，无需数据迁移。
